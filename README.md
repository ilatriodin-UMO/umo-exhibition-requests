# UMO — отдельная форма заявок с выставки

Готовый проект для GitHub Pages + Supabase. Существующий umo-partner-pulse и прежний сайт не изменены. Статус: код и локальные проверки готовы; рабочая база и публикация ещё НЕ настроены.

## Состав

- site/ — статическая форма и отдельный кабинет владельца; публикуется на GitHub Pages.
- supabase/setup.sql — отдельные таблицы exhibition_requests, exhibition_owners и функции. Запускается один раз администратором Supabase.
- .github/workflows/pages.yml — публикация папки site после push в main.
- tests/database.test.mjs — проверка настоящего PostgreSQL через PGlite: отправка, RLS, запрет чтения/изменений, права владельца, лимиты и защита от дублей.

## Запуск

1. Создать отдельный репозиторий umo-exhibition-requests в GitHub, загрузить проект. Для бесплатного GitHub Pages обычно нужен публичный репозиторий; записи заявок в GitHub не хранятся.
2. В Supabase проекта xufsoxmcsvxqujgijtqx выполнить supabase/setup.sql. Скрипт не меняет partner_requests, employees или их права. Повторно не запускать без проверки существующей схемы.
3. В GitHub Settings → Pages выбрать GitHub Actions. После публикации взять фактический адрес сайта.
4. В Supabase Authentication → URL Configuration добавить точный адрес owner.html нового сайта в Redirect URLs. Существующие адреса и Site URL не менять.
5. Открыть owner.html, запросить ссылку на свою почту, перейти по ней. Если почтовая доставка в проекте не настроена, настроить SMTP Supabase. Сам вход ещё не даёт право читать заявки.
6. В Authentication → Users найти подтверждённую учётную запись владельца. В SQL Editor выполнить отдельно, подставив её UUID:

```sql
insert into public.exhibition_owners(user_id)
values ('UUID-ПОДТВЕРЖДЁННОГО-ВЛАДЕЛЬЦА')
on conflict do nothing;
```

7. Повторно открыть кабинет: проверить выгрузку. В отдельном браузере без входа проверить отправку и запрет чтения таблицы. Только после этого печатать QR-код нового адреса.

В config.mjs указан уже используемый вашим проектом публичный ключ Supabase. Это не секретный ключ администратора. Правила доступа задаёт база. Не помещайте service_role, sb_secret, пароли или данные заявок в репозиторий.

## Поведение

Пять обязательных полей: телефон, имя, ИНН, модель, количество. Посетитель не регистрируется. Серверная функция проверяет поля и контрольные цифры ИНН, ограничивает 10 заявок в час на телефон и 2000 суммарно, возвращает только подтверждение без чужих данных. Повтор UUID не создаёт дубль. Анонимным пользователям запрещены прямое чтение, добавление, изменение и удаление строк; запись идёт только через проверяющую функцию.

Авторизация владельца — Supabase Auth, без ChatGPT. Чтение разрешено только пользователю, добавленному администратором в exhibition_owners, с подтверждённой почтой. Для обычных вошедших пользователей таблица остаётся закрытой. Выгрузка — настоящий XLSX, до 20 000 строк за выбранный период. Телефон и ИНН текстовые, ввод не превращается в формулы.

Данные прежнего сайта автоматически не переносятся: это отдельный проект. Доступность GitHub Pages и Supabase без VPN необходимо проверить с телефона/сети выставки; факт размещения сам по себе не гарантирует доступность у каждого оператора.

## Локальная проверка

Node.js, затем npm ci и npm test. Тесты используют отдельную временную базу в памяти и не обращаются к рабочим данным. Для просмотра можно запустить любой локальный статический сервер с корнем site. Реальная отправка до применения setup.sql ожидаемо не работает.
